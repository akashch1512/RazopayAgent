Razorpay Autonomous Recovery Agent API

Welcome to the Razorpay Agent Developer Reference. This API powers an enterprise-grade autonomous recovery system designed to monitor failed transactions, paused subscriptions, payment link expirations, and bank downtime events across multiple sub-merchants on Razorpay.

The system ingests real-time webhooks, validates cryptographic HMAC-SHA256 signatures, deduplicates repeat retry storms, aggregates multiple deliveries into unified Recovery Cases, and dispatches intelligent recovery workflows (automated WhatsApp outreach, SMS, IVR calls, and smart retry schedules).

Key Architecture Rule: Recovery is centered on Cases, not individual events. If an end customer tries to checkout 5 times with a failing card within 3 minutes, the system receives 5 webhooks, appends all 5 to the event audit history, but maintains exactly 1 active Recovery Case for the AI agent to solve.

Authentication & Security

The API utilizes three distinct layers of security depending on the endpoint category:

  • Sub-Merchant OAuth 2.0: Sub-merchants grant permissions through Razorpay's OAuth Authorization Code grant flow. Access and refresh tokens are encrypted at rest in PostgreSQL using AES-256 Fernet encryption.
  • Webhook Signature Verification: Inbound webhooks from Razorpay deliver an X-Razorpay-Signature header. The server calculates an HMAC-SHA256 digest of the raw request payload using the sub-merchant's unique webhook secret and compares digests with constant-time equality.
  • API Token / JWT Bearer: Admin and dashboard endpoints can be protected by standard Bearer JWT tokens configured via settings.JWT_SECRET_KEY.
Webhook Signature Header: All requests to /api/webhooks/razorpay must include the header:

X-Razorpay-Signature: <hex_hmac_sha256_digest>

Recovery Lifecycle & States

A recovery case transitions through the following lifecycle stages:

Status Description
RECEIVED The case was just created from an inbound webhook and has not yet been queued to the broker.
QUEUED Enqueued into Celery / Redis with an assigned priority score (1 to 10).
PROCESSING Claimed by an autonomous agent worker; recovery outreach or simulation tool execution is actively running.
PROCESSED The agent completed its scheduled steps (outreach sent, notification dispatched). Case remains monitorable if fresh events arrive.
RESOLVED A resolving event arrived (e.g., payment.captured or subscription.activated). Case is closed successfully.
FAILED A transient execution failure occurred; reconciler will retry automatically using exponential backoff.
DEAD Retry attempts exhausted without resolution; case is escalated for human support review.

HTTP Error Codes

Code Reason Resolution / Meaning
200 OK Success Request succeeded.
201 Created Resource Created Entity successfully registered (e.g. pending business onboarding).
400 Bad Request Client Error Invalid JSON payload, missing required query parameters, or denied OAuth grant.
404 Not Found Entity Missing The requested business_id, case_id, or event_id does not exist in the database.
409 Conflict Duplicate Entity Business with the specified reference_id has already been registered.
422 Unprocessable Schema Validation Failed Pydantic schema validation (data type mismatch, length constraints violated).
502 Bad Gateway Upstream Provider Failure Communication failure when contacting Razorpay API or OAuth endpoints.
503 Unavailable Database / Persistence Down Server could not safely store the webhook event; Razorpay is instructed to redeliver via backoff.

Initiate Business Onboarding

/api/onboard-business/

Step 1 of Onboarding: Registers a new sub-merchant in PENDING status, generates a secure random state token, and builds the official Razorpay OAuth authorization URL.

Redirect the merchant business owner to the returned authorization_url. Once they approve access, Razorpay redirects back to /api/onboard-business/callback with the grant code.

Request Body (JSON)

Field Type Description
name
Required string (1..255)
Legal or trading business display name (e.g. "Acme Retail Store").
reference_id
Required string (1..255)
Unique external identifier for your platform's merchant entity (e.g. "merchant_ref_98231").
contact_email
Optional email
Primary merchant contact email address for alerts and notifications.
scope
Optional string
OAuth permission scope override. Defaults to "read_write".

/api/onboard-business/callback

Step 2 of Onboarding: Target redirect endpoint called by Razorpay when the merchant authorizes access.

The server validates the state token, exchanges the authorization code for live OAuth credentials, securely encrypts tokens, automatically provisions a dedicated webhook subscription on the merchant's Razorpay account for all recovery event triggers, and updates the business state to ACTIVE.

Receive Razorpay Webhook (Ingress)

/api/webhooks/razorpay

The high-throughput ingress endpoint where Razorpay delivers all subscribed webhook events for every onboarded merchant business.

Processing Pipeline:

  1. Merchant Lookup: Resolves merchant via account_id in the payload envelope.
  2. Signature Verification: Validates X-Razorpay-Signature using the sub-merchant's secret.
  3. Normalization & Deduplication: Generates a SHA-256 dedupe key combining the event ID / body.
  4. Case Upsertion: Keys the recovery case by order (order:<id>) or entity (entity:<id>). Subsequent failures merge into the case.
  5. Priority Calculation: Computes dynamic priority (1: highest to 5: default) based on transaction value.
  6. Celery Worker Dispatch: Enqueues the case if new or re-opened; acknowledges Razorpay with 200 OK.

HTTP Headers

Header Required Description
X-Razorpay-Signature
 Required HMAC-SHA256 signature generated by Razorpay with the merchant's webhook secret.
X-Razorpay-Event-Id
 Optional Unique delivery event ID used for idempotency tracking.
